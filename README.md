# snakemake-sra-rnaseq

A reproducible Snakemake workflow that takes a public SRA study accession and returns a gene-level count matrix, QC report, and DESeq2 differential expression results.

Every dependency is pinned in per-rule conda environments, the sample sheet is generated by SQL against the SRA metadata tables in BigQuery rather than assembled by hand, and the DAG is dry-run tested in CI on every push.

```
SRA accession
   ↓  prefetch + fasterq-dump
FASTQ
   ↓  fastp (adapter/quality trimming) → FastQC
trimmed FASTQ
   ↓  salmon (selective alignment, decoy-aware index)
transcript quantifications
   ↓  tximport (lengthScaledTPM)
gene count matrix
   ↓  DESeq2 (+ apeglm LFC shrinkage)
results tables, MA plots, PCA, MultiQC report
```

## Quickstart

```bash
git clone https://github.com/masondandrus/snakemake-sra-rnaseq
cd snakemake-sra-rnaseq

# 1. Build the sample sheet from SRA metadata in BigQuery
python workflow/scripts/fetch_sra_metadata.py --study SRP123456 --audit
python workflow/scripts/fetch_sra_metadata.py --study SRP123456 --out config/samples.tsv

# 2. Point config/config.yaml at the right reference and set your contrasts

# 3. Check the plan, then run
snakemake -n
snakemake --use-conda --cores 16
```

Outputs land in `results/`: `counts/gene_counts.tsv`, `qc/multiqc_report.html`, `deseq2/*.results.tsv`, and diagnostic PCA/MA plots.

## Building the sample sheet with SQL

The SRA's metadata is queryable in BigQuery (`nih-sra-datastore.sra.metadata`), so run accessions, library layout, and submitter sample attributes can be pulled with a query instead of clicked out of the Run Selector. `resources/sra_metadata.sql` does this and normalises the result into the four columns the workflow requires: `run`, `sample`, `condition`, `library_layout`.

Importantly, sample attributes are submitter-defined key/value pairs, not fixed columns, so, e.g., `treatment_sam` in one study is `condition_sam` or `genotype_sam` in the next. Run the audit query first, as it lists every attribute key a study actually used, with example values, then edit the `COALESCE` block to match. It is critical at this point to ensure proper labeling.

```bash
python workflow/scripts/fetch_sra_metadata.py --study SRP123456 --audit
```

## LLM-assisted sample sheet curation (optional)

`workflow/scripts/curate_samples.py` uses the Claude API to propose `condition`
assignments from submitter free text — the cases the SQL `COALESCE` block cannot
reach, like a design written as "5 mg/kg cocaine, 24h withdrawal" inside
`source_name_sam`.

**It is deliberately not a Snakemake rule.** Model output is non-deterministic;
a model call inside the DAG would mean the same accession could yield different
counts on different days, which destroys the property this repo exists to
demonstrate. The script writes a proposal and a provenance record, you review
and accept, and the committed `samples.tsv` is what the pipeline reads. Every
number downstream traces to a reviewed, version-controlled artifact.

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # https://platform.claude.com

python workflow/scripts/fetch_sra_metadata.py \
    --study SRP123456 --dump-attributes resources/SRP123456.attributes.json

python workflow/scripts/curate_samples.py \
    --attributes resources/SRP123456.attributes.json          # propose only
python workflow/scripts/curate_samples.py \
    --attributes resources/SRP123456.attributes.json --accept # write sample sheet
```

The model is treated as untrusted input, not an authority. Responses are
rejected if they invent runs, drop runs, duplicate runs, or assign a condition
without quoting the attribute text it came from. Anything the model cannot
support is returned as `UNRESOLVED` for you to resolve by hand rather than
guessed. Runs below high confidence are flagged in the report. Candidate
covariates — batch, sex, collection date — are surfaced as suggestions for
`deseq2.design`; the script never edits the design itself.

Each run writes `*.curation_provenance.json` recording the model, temperature,
prompt hash, input hash, token usage, and the raw response. Commit it next to
the sample sheet.

Cost is a few cents per study at current API rates.

## Design decisions

**Selective alignment with a decoy-aware index.** Salmon's decoy-aware selective alignment reduces spurious mappings from unannotated genomic sequence, which otherwise inflate abundance for a subset of transcripts (Srivastava et al., 2020). The cost is a genome-sized index build; the benefit is quantification that holds up on experimental rather than simulated data.

**`countsFromAbundance = "lengthScaledTPM"`.** Corrects for differences in average transcript length across samples while producing values on a count scale, so DESeq2's negative binomial assumptions still hold.

**prefetch before fasterq-dump.** Streaming `fasterq-dump` directly against NCBI is the usual cause of silently truncated FASTQ files on large studies. `prefetch` is resumable, and the rule carries `retries: 3`.

**Layout-aware rule pairs rather than a checkpoint.** Paired- and single-end runs are handled by separate rules with distinct output patterns, so the DAG resolves statically from the sample sheet. Mixed-layout studies work without special handling.

**Intermediate FASTQs are `temp()`.** Raw and trimmed reads are deleted once consumed. A 40-sample study stays in the tens of GB rather than hundreds.

**Per-rule conda environments.** Each rule declares its own pinned environment (`workflow/envs/`), so the salmon and R toolchains never have to co-resolve. Versions are pinned to the minor release.

## Repository layout

```
config/
  config.yaml            reference URLs, tool parameters, design, contrasts
  samples.tsv            one row per SRA run
workflow/
  Snakefile              config parsing, input helpers, targets
  rules/                 download, qc, quant, de
  envs/                  pinned conda environments, one per toolchain
  scripts/               tx2gene.py, tximport.R, deseq2_init.R, deseq2_results.R
                         fetch_sra_metadata.py, curate_samples.py
resources/
  sra_metadata.sql       BigQuery sample-sheet query + attribute audit query
.github/workflows/ci.yml lint + dry-run on every push
```

## Configuration

| Key | Purpose |
| --- | --- |
| `reference.transcriptome_url` / `genome_url` | GENCODE FASTAs. Swap both together — the decoy index needs a matching genome build. |
| `salmon.kmer` | 31 by default; drop to 23–25 for reads under ~50 bp. |
| `salmon.libtype` | `A` infers strandedness; verify against `lib_format_counts.json`. |
| `deseq2.design` | Any DESeq2 formula over columns present in the sample sheet. |
| `deseq2.min_count` / `min_samples` | Pre-filtering threshold, independent of the design. |
| `contrasts` | `[factor, numerator, denominator]` per contrast; the key becomes the output filename. |

Non-human studies need the transcriptome and genome URLs changed. `tx2gene.py` parses GENCODE-style pipe-delimited FASTA headers; an Ensembl FASTA needs a GTF-derived map instead.

## Running on a cluster

```bash
snakemake --use-conda --profile <your-profile> --jobs 100
```

Rules declare `threads` and `mem_mb`. The salmon index build is the memory ceiling at roughly 32 GB for a decoy-aware human index.

## Testing

CI runs `snakemake --lint` and a full dry run against `.test/config.yaml` on every push, which catches wildcard, input-function, and DAG errors without downloading data. Run the same checks locally:

```bash
snakemake --lint
snakemake -n --configfile .test/config.yaml
```
